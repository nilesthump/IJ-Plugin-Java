# F0 开发与实际使用的异常处理讨论

更新：2026-10-16（Asia/Shanghai）。状态：讨论稿。权威状态为 `WORKING.json`；依据用户澄清 `evidence/user-turn-018.md`。尚未实现或冻结。

## 1. 已确认原则

| 场景 | 用户要求 |
| --- | --- |
| 开发过程 | 禁止兜底掩盖错误，错误暴露后定位修复 |
| 实际使用 | 异常要有明确提示，并进行降级处理 |
| 实施规模 | 继续遵循 MVP，不引入超出当前需要的通用框架 |
| 检索故障 | 实际使用提示后自动继续通识回答，明确标注课程检索失败、未使用课程证据；user-turn-019 |
| 正常无证据 | 无相关资料、未建课程库均自动通识回答，分别标注；user-turn-021。正常业务分支不等于异常兜底 |

不能将开发时暴露问题解释成让实际用户承受无提示失败；也不能将产品降级路径用于让开发验证在出错后仍显得通过。先前对运行时降级的全面禁令撤回。

## 2. 责任边界（提案）

核心解析、检索、模型与存储组件不随意捕获异常后返回空值、伪造结果或改走备用实现。异常携带原始原因及 session/request/source 等定位身份，传播到明确的任务/产品边界；资源照常释放。

开发/调试路径在该边界暴露原错误，不默认执行降级使功能看似成功。实际使用路径由边界记录错误及受影响阶段状态、向用户说明影响，并执行已定义的降级；同一故障只形成一次清晰提示，避免每层重复通知。检索失败后继续通识回答时，仅检索阶段标为失败，原回答任务仍在运行；不能先将任务终止为失败，再尝试接收降级结果。只有链路无法继续时才提交任务失败结果。

两种策略的选择在运行入口明确，具体配置方式实施时确定；不能根据一次异常猜测环境或偷偷切换。产品降级分支在开发中以明确的故障场景单独验证，不能为了“开发不兜底”而省略降级验证，也不能让该分支掩盖正常链路的缺陷。

`try-catch` 不是一律禁止的语法：禁止的是开发时掩盖问题，以及在各层随意吞错；实际使用边界为提示和降级进行有目的的异常处理是必要部分。未定义的异常在实际使用中也应提示并停止受影响操作，保留可用界面与数据，不擅自编造可继续的回答。

## 3. MVP 降级矩阵（提案）

| 故障 | 用户可见提示 | 有边界的降级 |
| --- | --- | --- |
| 新 PDF 解析、嵌入或入库失败 | 哪份资料/哪阶段失败，新版本尚未就绪 | 新代次不激活；已有就绪代次继续可用，并说明仍使用旧版本；首次导入失败则课程库不可用于 RAG |
| 方法/类自动上下文捕获失败 | 自动上下文未就绪，说明受影响部分 | 保留原选区和草稿、暂停当前发送并提供重新捕获入口，其他会话/已保存浏览能力继续；不把半套材料冒充完整上下文，不扩展为整项目读取 |
| 查询嵌入或课程检索失败 | “课程检索暂不可用”，区分正常无相关资料 | 按用户确认自动继续通识回答，保留原问题/代码及同一请求身份；回答明确标注检索失败、未使用课程证据，不伪造本轮课程引用 |
| 摘要/压缩失败 | “上下文整理失败”，说明是否还能继续本轮 | 仅在旧有效 checkpoint 加未覆盖原文、本次提交和本轮证据重建后仍满足预算时继续；否则暂停发送，保留材料并提供减少输入/重试整理入口 |
| 生成服务失败或流式响应中断 | 当前回答失败/未完成，已有部分不冒充完成 | 保留问题、代码与已保存历史，停止当前生成并提供重试；不自动更换服务或重复追加用户消息 |
| 草稿/消息/回答保存失败 | 明确显示未保存，不能显示已安全保存 | 保留可保留的内存内容；暂停依赖该次提交的后续发送，受影响写入停止；其他已验证可用的浏览/会话功能可继续 |
| session/checkpoint/布局读取失败 | 明确指出恢复不完整及受影响对象 | 不覆盖原始记录；仅展示能验证归属与完整性的记录。checkpoint 可从完整档案重新规划，布局可从会话列表重开；具体恢复选择单独验证 |
| 索引读取失败 | “课程索引不可用”，说明 RAG 受影响 | 历史聊天及可验证的托管 PDF 仍可浏览；提供重建入口。新的通识回答沿用上述检索失败规则 |
| 删除 session 未完成 | 明确提示删除未完成及失败原因，不能仅隐藏标签后宣称成功 | 保持该 session 的任务/延迟写入失效，保留再次完成清理的操作入口；仅在全部所属记录及缓存清除后报告删除成功，不清理共享课程库 |
| 未分类异常 | 当前操作失败及可用于反馈的错误标识 | 终止受影响操作，保留可用界面和已提交数据；记录完整原因供修复，不默认返回空结果或成功状态 |

降级不一定意味着继续调用 LLM；停止当前生成、保留输入并维持其他功能可用，也属于明确的能力降级。无法确定存储可靠性时，不能假定写入成功后继续发送。

## 4. 必须保持的边界（提案）

- **提示真实状态。** 正常无命中、课程库未导入、检索故障、摘要失败和生成失败分别表达；不能用“没有课程材料”掩盖网络异常。
- **正常无证据分支。** 无相关片段标注“无相关资料”，未建索引标注“未建课程库”，均自动继续且不伪造课程引用。正常分支在开发验证中也按定义运行；不得把解析/检索异常转换成这些状态。
- **回答有明确依据。** 检索故障后的通识回答说明课程检索失败、未使用本轮可验证课程证据；不使用摘要中的旧引用冒充新检索结果。
- **当前请求完整。** 旧 checkpoint 降级需重建并重新核算当前输入；不能复用上轮投影或无提示截断本轮代码。
- **保存事实不变。** 短事务、版本校验与 session 隔离继续适用；降级不清空损坏档案，不改写历史 PDF 版本，不激活未完成索引/摘要。
- **重试有限且可解释。** 不重复提交用户消息，不自动切换模型；具体压缩失败参数仍由任务执行成员确认。普通模型调用和依赖默认重试需纳入统一策略，不能叠加成隐藏循环。
- **诊断保留。** 用户获得简短提示和必要操作入口，开发者保留原始原因/堆栈及定位身份；日志不写入凭据。
- **诊断随会话删除。** 可识别某 session 的诊断/用量/错误记录纳入可按 session 清理的存储或文件，不把副本散落在不可定位的缓存/日志；删除该 session 时一起清除。删除后的迟到异常不新建诊断或恢复该 session。

MVP 优先采用一个清晰任务边界及必要降级分支，不建立全局万能 catch、通用修复系统或复杂熔断平台。

## 5. 验证与归属（尚未执行）

1. 开发正常链路发生同样故障时，能观察原始异常，不能因备用回答而通过功能验证。
2. 明确测试实际使用策略时，检索/摘要/生成/存储故障均有提示和对应降级；未知错误停止当前操作。
3. 摘要降级继续时，输入包含当前问题、代码与实际证据且符合预算；不符合则暂停发送。
4. 重试或恢复不会重复追加消息、跨 session 回包、把部分回答标为完成或覆盖原始资料。
5. 标签关闭后，实际使用的后台故障仍能由项目公共入口提示；session 删除后则不写回其诊断/回答/摘要记录，也不显示可重开该 session 的旧通知。

沿用 5:1:1:1：负责人提供任务边界、错误契约与降级编排；各成员暴露所属模块错误并提交必要故障样例，成员丙负责提示与操作入口的呈现。模型、预算及失败参数的实施决策仍由对应执行成员承接。

## 6. ReAct 多步骤的故障边界（提案）

多步补查故障不能在保留已注入课程证据的上下文中宣称未使用课程证据。沿用用户确认的通识分支时，先失效旧 branch 的模型/工具及存储写入权，至多一次基于冻结原问题/代码/历史重建合法无本轮证据输入，旧步骤只保留过程档案；新正文与证据独立保存，禁用后续课程工具。旧步骤预览明确失效，通识生成失败直接结束。正常补查无命中不清除此前成功证据；生成断流不按检索故障触发第二次请求。

具体协议无法合法重建、工具参数/配对错误或执行限额达到时，开发暴露原错，实际使用提示并停止受影响循环，不伪造观察或成功终止。详细算法及验证边界见 `REACT_ORCHESTRATION.md`。

## 7. 保留显示与过滤模型输入

user-turn-032 确认停止、重试、超限及中断不清除已生成/渲染内容；这些不完整生成记录不进入后续模型、摘要或协议投影。原问题/代码和可验证的已提交数据继续保留，错误提示/状态不得被误当作模型回答内容。核心停止协调方冻结已接收内容并有条件保存终止快照；网络回调无权在失效后追加。保存失败提示未保存，不能以 UI 已显示宣称耐久成功。

停用先撤新操作和旧配置 epoch；只有停用后可改 API key。资料更换失败保留所选资料旧版/检索代次，MD5 重复和正常空结果与故障分开。依据及实现提案见 F0_BEHAVIOR.md、COURSE_LIBRARY.md，详细验收/排期仍待定。
